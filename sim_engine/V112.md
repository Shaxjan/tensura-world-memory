# Simulation Engine v1.0.12 — Runtime Fast Path Reliability Repair

v1.0.12 is a transport-only repair. Gameplay semantics remain those of v1.0.10/v1.0.11.

Observed LIVE failure after v1.0.11:
- `r000019`, `q-chat-20260824-what-doing-001.json`, and `q-chat-20260824-what-doing-002.json` were enqueued but produced no authoritative gameplay event;
- the first fast request omitted `request_id` because MASTER did not require it, while the processor did;
- the second fast request used top-level `raw_text`, while the processor required a nested `request` object;
- retries created multiple input files for the same intended player action;
- the aggressive shallow/sparse workflow made triggering-commit identification brittle once main advanced.

Repair rules:
1. Canonical fast request uses `request.raw_text` and does not require `request_id`.
2. A top-level `raw_text` is accepted only as a compatibility normalization when no `request` object exists.
3. Conflicting nested/top-level raw text is rejected.
4. `expected_last_gameplay_turn_key` remains fail-closed.
5. `event_key` duplicates are rejected before a new journal write.
6. The workflow identifies the request on the exact triggering SHA before resetting to fresh authoritative main.
7. The workflow returns to the proven full checkout + Python setup path. Reliability takes priority over a few seconds of runner setup.
8. Every processed v1.0.12 request creates a non-authoritative receipt under `runtime/request_receipts/`.
9. Processor failures also create a failure receipt when the workflow reaches the processor.
10. One user action must create one request only. Do not enqueue duplicates while waiting.

The three failed v1.0.11 transport attempts are never executed automatically. v1.0.12 activation records them as superseded transport artifacts and creates superseded receipts. No gameplay action is inferred from them.

Activation is zero-time and transport-only: no player/NPC action, movement, money, memory, relationship, personality, or world-state change.
