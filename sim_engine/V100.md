# Tensura Simulation Engine v1.0 — Authoritative Runtime Cutover

v1.0 is the first architecture intended to become the live source of truth. It does not treat a successful narration as a state mutation.

## What v1.0 adds

### Typed pending-resolution bridge

v0.10 could safely create `pending_resolution`, but an unresolved result still needed an engine-owned way to become fact. v1.0 adds that bridge.

Supported resolution families are deliberately narrow:

- local navigation/search;
- NPC response/consent;
- object hand-off acceptance;
- generic world outcome.

The resolver accepts only enumerated outcomes and bounded fields. It may update only the state owned by that resolution type. It cannot silently alter cash, combat state, power, project funds or unrelated hidden state.

A prospective resolution is tagged `PROSPECTIVE_ENGINE_RESOLUTION`; it is not evidence about historical canon before cutover.

### Narration is not authority

A `scene_pending` turn may now be narrated while the outcome remains unresolved. Narration cannot make the pending outcome true. If the scene later produces a concrete NPC/world result, that result must pass through the typed resolver first.

### Append-only runtime journal

Ordinary live state no longer requires rewriting the full portable checkpoint.

The persistent layout is:

- `runtime/runtime_state.json` — tiny authoritative pointer;
- `runtime/checkpoints/cutover_v159.json` — immutable base checkpoint produced at cutover;
- `runtime/journal/jNNNNNN.json` — immutable prospective runtime events.

Normal write order is strict:

1. execute the event in the engine;
2. write one immutable journal event containing request + result + before/after state hashes;
3. update the tiny runtime pointer to the new journal sequence and head hash.

The journal is replayed from the immutable checkpoint on a fresh runtime. Replay must reproduce every expected state hash. A gap, tampered event or hash mismatch fails closed.

`runtime_journal` is deliberately excluded from the portable world-state hash so the audit trail does not make its own state hash self-referential.

### Rollback

The exact pre-cutover `live_state.json` object and its Git blob SHA are embedded in the cutover metadata and runtime pointer. Legacy LIVE v159 is frozen, not deleted. Rollback therefore has a precise anchor rather than a reconstructed approximation.

## Cutover rehearsal

The v1.0 rehearsal must pass all of the following without advancing the actual v159 base:

1. re-prove the v0.10 local-search + autonomy shadow gate on an isolated copy;
2. create a candidate v1.0 checkpoint;
3. execute `Иду искать Боргу.` as a journaled player event;
4. resolve that search with a typed `not_found` result that does not invent Borga's location;
5. execute an authoritative wait event;
6. replay all three journal entries from the same checkpoint in a fresh database;
7. require the same full portable world-state hash;
8. verify the exact legacy pointer/blob rollback anchor;
9. export a clean final checkpoint whose time, region and personal cash are still the untouched LIVE v159 values.

Only then may the generated runtime pointer be marked `prepared`.

## Actual switch

CI generation of a `prepared` pointer is not itself the live switch. The final activation is a separate repository operation:

- verify `live_state.json` has not advanced since checkpoint generation;
- merge the tested v1.0 code + generated checkpoint;
- change `runtime/runtime_state.json.mode` from `prepared` to `engine_authoritative`;
- freeze `live_state.json` as the legacy rollback pointer and point it to the v1.0 runtime;
- update `MASTER_SAVE_PROTOCOL.md` so new masters load the runtime pointer/checkpoint/journal first.
