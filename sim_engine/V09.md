# Tensura Simulation Engine v0.9 — Guarded Cutover & Portable Runtime

v0.9 does not manufacture missing combat, skill, relationship, market or route numbers just to make a migration checklist green.

## Five former calibration blockers

The previous five calibration items are converted into explicit prospective feature policy:

- player power — `guarded_unknown`;
- player skills — `guarded_unknown`;
- relationship mechanics — qualitative history remains authoritative; numeric mechanics may begin only from prospective events;
- markets — `observation_first`;
- routes — `observation_first`.

These policies are `NON_CANON_MECHANICAL`. They may control future resolution once calibrated or observed, but they are never evidence about what Arlequino or an NPC historically was.

Missing numeric data therefore does not become zero, average, default rank, default trust, a laboratory price or a laboratory journey time. The corresponding command remains disabled until its required mechanical state exists.

## Portable runtime checkpoint

v0.9 adds a deterministic JSON handoff format for the SQLite runtime:

- format: `TENSURA_ENGINE_RUNTIME`;
- schema version: 9;
- canonical JSON body;
- SHA-256 state hash;
- all ordinary runtime tables are serialized deterministically;
- SQLite BLOB values are base64 encoded;
- import validates format/schema/hash before changing state;
- import repopulates a fresh v0.9 database, runs `PRAGMA foreign_key_check`, then re-exports and requires the same canonical state hash.

`campaign_archives` is deliberately excluded from the portable checkpoint. It is a large raw copy of repository source history and can be reproduced from GitHub during migration; duplicating it on every ordinary runtime handoff would make saves unnecessarily heavy. `portable_checkpoint_audit` is also excluded so checkpoint transport does not make its own state hash self-referential.

The ordinary portable state must therefore be small enough to hand from one master/session to another without replaying the entire repository history.

## Shadow handoff

The real-repository rehearsal performs:

1. migrate the current GitHub LIVE state through v0.8 money reconciliation;
2. install guarded prospective mechanics policy;
3. export one portable runtime checkpoint;
4. create a fresh SQLite runtime;
5. import the checkpoint;
6. require identical portable state hash and identical critical player state;
7. submit a deliberately unsupported one-minute wait command;
8. require `blocked_by_migration` and no critical-state mutation.

No `runtime_state.json` is committed as authoritative yet. The old GitHub LIVE pointer remains source of truth until the final cutover gate is passed.

## Remaining live-cutover blockers

v0.9 intentionally leaves two runtime blockers active:

### `scene_action_bridge_not_implemented`

The deterministic parser covers a limited command vocabulary. Normal live scenes also contain dialogue, singing, local movement, object hand-offs, performances and many other player-controlled actions. Those actions still need a structured state-transition bridge so the narrator never has to mutate authoritative state outside the engine.

### `autonomy_commitment_execution_not_wired`

Imported NPC tasks, mail, festival/tournament work and other autonomous commitments are preserved, but they are not yet connected to an executable prospective scheduler/resolution API. Time advance must remain gated until important off-screen work can actually progress instead of freezing.

`live_cutover_ready` therefore remains false in v0.9 even if the portable checkpoint roundtrip passes.

## Next gate

v0.10 should solve those two runtime blockers, then run a true shadow scene against the current LIVE checkpoint. Only after that should the engine be allowed to become the authoritative live runtime.
