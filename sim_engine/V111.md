# Simulation Engine v1.0.11 — Runtime Fast Path

v1.0.11 changes transport, not gameplay semantics. All v1.0.10 causal NPC-response, memory, autonomy, living-scene and money rules remain authoritative.

## Problem

A normal turn previously required the gameplay chat to read the LIVE pointer before it could allocate `rNNNNNN`, enqueue the request, then wait for GitHub Actions and read the result. The GitHub request-to-runtime commit for `r000017` was about 11 seconds by repository commit timestamps; the much larger end-user latency came from additional model/tool round-trips and polling around that transport.

## Fast request

Normal synchronized gameplay uses an immutable queue file with format:

```json
{
  "format": "TENSURA_FAST_TURN_REQUEST",
  "schema_version": 1,
  "request_id": "unique-client-request-id",
  "event_key": "unique-gameplay-event-key",
  "event_type": "player_turn",
  "expected_last_gameplay_turn_key": "last-turn-seen-by-this-gameplay-chat",
  "request": {"raw_text": "verbatim user action"}
}
```

The queue filename is `runtime/requests/q-<unique-id>.json`. It does **not** contain or reserve journal sequence.

At execution time, under the existing serialized authoritative runtime lock, the processor reads the fresh pointer and assigns `seq = journal_seq + 1`.

## Optimistic gameplay-context guard

The fast request must name the last gameplay turn visible to the gameplay chat. The processor compares it to current `runtime/session_state.json:last_turn.event_key`.

- Zero-time technical activations preserve `last_turn`, so they do not force a preflight read.
- If another gameplay turn happened first, the keys differ and the fast request fails closed before engine mutation.
- Recovery then refreshes authoritative session/pointer and requires an explicit retry; no action is silently replayed on a changed gameplay context.

This guard is not a substitute for engine validation. It only safely removes the normal preflight pointer round-trip.

## Normal synchronized turn path

1. Gameplay chat already holds the prior confirmed `session_state` in context.
2. Create one unique `q-*.json` fast request using the prior `last_turn.event_key`.
3. GitHub Actions serializes execution, loads the newest authoritative runtime, allocates journal sequence, executes the engine, and commits journal + pointer + session.
4. Gameplay chat reads `runtime/session_state.json` once after processing and narrates only the confirmed result.

No routine full replay, journal read, or pointer preflight is required in the synchronized happy path.

## Workflow latency reduction

`runtime-turn.yml` in v1.0.11:

- removes `actions/setup-python` from the per-turn path and uses the hosted runner's `python3`;
- uses sparse checkout for only `sim_engine` and `runtime`;
- derives the triggering request from the push event instead of requiring history traversal;
- removes the unconditional extra `git fetch/reset` pass;
- keeps the existing authoritative concurrency group;
- retries with rebase only if the final push races a non-runtime code commit.

GitHub Actions runner startup still imposes an infrastructure floor. v1.0.11 reduces avoidable repository/model round-trips; it does not claim that GitHub-hosted Actions can provide a guaranteed 1–5 second turn. A future always-on runtime service can reuse the same fast request and guard semantics.

## Compatibility

Legacy `TENSURA_TURN_REQUEST` / `rNNNNNN.json` remains accepted by the v1.0.11 processor when its explicit seq exactly matches current `journal_seq + 1`. This is recovery/backward compatibility, not the normal fast path.

## Activation

Activation is transport-only and zero-time:

- compact current v1.0.10 head;
- add one `runtime_fast_path_activation` journal event;
- `before_hash == after_hash`;
- preserve time, place, money, Borga memory/personality/relationships, NPC responses and last gameplay turn;
- enable fast-path flags in the pointer/session read-model.
