# Tensura World Memory — Authoritative Runtime v1.0 Save Protocol

Цель: вести живую симуляцию через проверяемый движок, сохранять изменения компактно и быстро, не подменять `UNKNOWN` догадками и иметь точный rollback к последнему legacy-состоянию.

## 1. Авторитетная архитектура после cutover

### `runtime/runtime_state.json`
Это **главный указатель текущего состояния**. Если `mode` = `engine_authoritative`, текущий LIVE определяется только указанным base checkpoint и журналом до `journal_seq` включительно.

Ключевые поля:
- `base_checkpoint` — базовый portable checkpoint;
- `base_state_hash` — его проверочный SHA-256 состояния;
- `journal_dir` — каталог неизменяемых runtime events;
- `journal_base_seq` — sequence, уже включённый в base checkpoint;
- `journal_seq` — последний подтверждённый event;
- `head_state_hash` — ожидаемый hash состояния после replay до `journal_seq`;
- `legacy_rollback` — точная pre-cutover legacy-точка.

### `runtime/checkpoints/`
Portable snapshots движка. `runtime/checkpoints/cutover_v159.json` — неизменяемая стартовая база v1.0 и аварийный anchor. Не переписывать её.

### `runtime/journal/jNNNNNN.json`
Append-only события после cutover. Один файл = один авторитетный переход движка. Пропуск sequence, подмена файла или несовпадение before/after hash должны останавливать replay.

### `live_state.json`
После v1.0 это **замороженный legacy-маркер**, а не текущий SAVE. Поля `v=159` и `delta=live_v159` сохраняются для совместимости и rollback. Если файл содержит `runtime: "runtime/runtime_state.json"`, новый мастер обязан перейти к runtime pointer.

### `world_save.json`, `live_v*/`, `memory/`
Это исторический архив, pre-cutover deltas и категорийные индексы. Они полезны для широкого контекста и аудита, но не имеют права перекрывать более новый runtime journal.

### `song_archive/` и `song_fragments/`
Песни живут отдельно от runtime-состояния. Их правила остаются в `rules/SONG_ARCHIVE_WRITE_RULE.md` и `memory/songs.json`.

## 2. Приоритет источников

1. Последняя прямая коррекция пользователя и ещё не сохранённое действие текущего хода.
2. `runtime/runtime_state.json`, если `mode=engine_authoritative`.
3. Указанный `base_checkpoint` + строго `j(journal_base_seq+1)...j(journal_seq)`.
4. Последняя подтверждённая typed scene resolution / engine result из runtime.
5. Замороженный `live_v159/delta.json` и старые LIVE deltas — только для pre-cutover истории и rollback.
6. `world_save.json`, GitHub history и `memory/` для широкого исторического контекста и аудита.
7. Память отдельного чата.

Прямая пользовательская коррекция имеет приоритет над противоречащей старой записью, но изменение текущего состояния должно быть проведено через движок/runtime event, а не только написано в прозе.

`UNKNOWN` всегда остаётся `UNKNOWN`, пока не появится причинное наблюдение, явная калибровка или прямое уточнение пользователя.

## 3. Старт нового чата / нового мастера

1. Прочитать `MASTER_SAVE_PROTOCOL.md`.
2. Прочитать `runtime/runtime_state.json`.
3. Убедиться, что формат `TENSURA_RUNTIME_POINTER`, engine `1.0`, mode `engine_authoritative`.
4. Загрузить `base_checkpoint`.
5. Прочитать только журнал после `journal_base_seq` и не дальше `journal_seq`.
6. Replay должен привести к `head_state_hash`. Использовать `sim_engine/v100_repository.py` / `WorldV100`, когда доступно исполнение Python.
7. Только после успешной реконструкции продолжать авторитетную симуляцию.
8. `live_state.json` и `live_v159` читать как legacy history/rollback, а не как текущую точку.

Если движок или проверяемый replay технически недоступен, нельзя компенсировать это выдуманной мутацией состояния. Можно обсуждать сцену, но новый авторитетный state transition должен дождаться исполнимого runtime.

## 4. Нормальный runtime-ход

Пользовательский текст передаётся движку дословно как `player_turn`.

Если действие имеет полностью определяемый движком результат — движок возвращает результат и новый state hash.

Если результат зависит от мира/NPC и ещё не установлен, ход получает `scene_pending`. Мастер может описать начало действия и воспринимаемую сцену, но не имеет права в прозе превратить pending в факт.

Конкретный внешний результат оформляется отдельным `scene_resolution` через typed resolver. После этого его можно нарративно показать пользователю.

Наррация сама по себе не является источником истины и не должна менять деньги, время, локацию, владение, отношения, знания или другие поля состояния.

## 5. Нормальное сохранение — две маленькие GitHub-записи

Для каждого авторитетного runtime transition:

1. Выполнить событие в движке и получить `before_hash`, `after_hash`, request и result.
2. Создать **один новый** `runtime/journal/jNNNNNN.json`.
3. Только после успешной записи event обновить `runtime/runtime_state.json`: увеличить `journal_seq` и поставить соответствующий `head_state_hash`.

Никогда не обновлять pointer раньше journal event. Не делать обе записи параллельно.

Нормальный ход **не создаёт новый `live_vNNN`** и не переписывает `world_save.json` или полный base checkpoint.

GM narration не требует отдельного journal event, если она не несёт отдельного авторитетного перехода. Точный пользовательский текст уже хранится в request события; важный внешний исход должен быть частью typed resolution/result.

## 6. Sequence и SHA conflict

Перед новой записью прочитать свежий `runtime/runtime_state.json`.

Следующий event = `journal_seq + 1`. Если такой файл уже существует или pointer изменился:
- не перезаписывать event;
- получить свежий pointer;
- восстановить runtime до его `head_state_hash`;
- проверить, был ли текущий turn уже сохранён по `event_key`;
- только затем продолжить с новым sequence.

Append-only journal-файл после подтверждения не редактировать и не переиспользовать.

## 7. Periodic checkpoint / compaction

Ориентир — примерно каждые 25 авторитетных runtime events, в конце крупной арки/дня или перед тяжёлой миграцией.

Процесс:
1. Replay текущего base + journal до `journal_seq`.
2. Проверить `head_state_hash`.
3. Экспортировать новый portable checkpoint в новый файл.
4. Проверить roundtrip этого checkpoint в чистой базе.
5. Записать checkpoint.
6. После успешной записи обновить pointer: новый `base_checkpoint`, его hash и `journal_base_seq = journal_seq`.

Старые journal files и `cutover_v159.json` не удалять автоматически: они остаются аудитом/rollback chain.

## 8. Typed pending resolutions

Обычная сцена не даёт мастеру права свободно менять SQLite/JSON.

Допустимые v1.0 resolution families:
- локальный поиск/навигация;
- ответ/согласие NPC;
- принятие передачи предмета;
- ограниченный world outcome.

Resolver принимает только предусмотренные outcome и поля и меняет только состояние, принадлежащее этому outcome.

Нельзя использовать generic resolution для обхода отдельных механик боя, денег, магии/лечения, межрегионального travel, рынка, силы или навыков.

## 9. Экономика и неопределённые механики

- 100c = 1s; 100s = 1g.
- Личная касса отдельно от promo/project funds, обязательств и денежных float у порученцев.
- После реально завершённого публичного выступления: income / expense / net / new personal cash.
- `ECONOMY_MODEL_v1` остаётся правилом экономики; отсутствие текущей цены/ликвидности не заменяется лабораторным значением.
- Неизвестный маршрут, цена, сила, навык или числовые отношения остаются guarded/observation-first, пока не возникнет причинная калибровка.
- Текущий остаток instrument float Верна остаётся `UNKNOWN`, пока не будет причинного отчёта/возврата/расхода.

## 10. Контроль персонажа, NPC и знания

- Арлекино/Маэстро полностью контролируется пользователем: не придумывать его реплики, решения, чувства и значимые действия.
- NPC и мир автономны; время должно двигать их активные commitments через runtime scheduler.
- Знание NPC должно иметь причинный канал: SOURCE -> TRANSMISSION -> TIME -> RECIPIENT.
- Не передавать NPC сведения из чужих приватных сцен.
- Только Рена говорит «павлин».
- Jura — регион; JTF ещё нет.
- Falmuth, не Farmenas.
- Поручение Верна в Дваргон не связано с Ореном.
- Гарет и Верн знают точную гостиницу в мире, но её название неизвестно GM и не должно быть придумано.

## 11. Ретконы

Прямая коррекция пользователя отменяет противоречащую старую запись.

После cutover реткон текущего состояния должен быть отдельным проверяемым runtime transition/repair event. Не редактировать старый immutable journal event задним числом.

Отменённую старую версию можно сохранять для аудита, но нельзя снова выдавать за канон.

## 12. Rollback к legacy v159

В `runtime/runtime_state.json.legacy_rollback` хранится точный исходный объект `live_state.json` и его Git blob SHA.

Emergency rollback:
1. Остановить новые runtime writes.
2. Проверить, что rollback anchor соответствует сохранённому blob SHA.
3. Сохранить/заархивировать текущий runtime pointer и journal head.
4. Восстановить **ровно** объект `legacy_rollback.pointer` как `live_state.json`.
5. Пометить runtime pointer `mode=rollback` или изолировать его от live-загрузки.
6. Продолжать от v159 только после явного решения; не переносить частично новые runtime events в legacy автоматически.

Rollback — аварийная операция, а не обычный способ отменить неудачный игровой исход.

## 13. Песни

- Одна песня = один полный UTF-8 файл, когда это технически возможно и файл реально проверен.
- `FULL_CANONICAL` ставится только после обратного чтения полного файла.
- Не доверять названию коммита `full exact` без проверки содержимого.
- Если файл обрезан — удалить/карантинировать его и понизить статус.
- Если полного текста нет, не использовать оригинал, web, пересказ или догадку для заполнения пользовательской адаптации.
- `PARTIAL_EXACT` хранить в `song_fragments/`.
- `TEXT_LOST` сохраняет факт песни/исполнения, но не фальшивый текст.
- После нового полного пользовательского текста: сохранить целиком одним файлом и проверить чтением.

## 14. Нельзя

- продолжать создавать обычные `live_vNNN` после engine v1.0 cutover;
- считать `live_state.json` текущим SAVE, когда он помечен `legacy_frozen`;
- обновлять runtime pointer до успешной записи соответствующего journal event;
- редактировать подтверждённый journal event;
- придумывать `UNKNOWN`;
- смешивать личные и проектные деньги;
- решать за Арлекино;
- давать NPC невозможные знания;
- разрешать pending outcome только текстом мастера;
- считать обрезанный текст песни полным;
- молча восстанавливать потерянную пользовательскую адаптацию по оригиналу.
