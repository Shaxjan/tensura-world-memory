# Tensura World Memory — ONE-WRITE Save Protocol

Цель: обычный checkpoint должен требовать **одну маленькую запись в GitHub**, а не переписывание большого SAVE.

## 1. Файлы

### `live_state.json`
Главный оперативный источник истины во время игры.

Хранит только актуальное состояние:
- `save_version`;
- world time;
- локацию/состояние/кассу Маэстро;
- `last_scene.summary` и `continue_from`;
- живые статусы важных NPC;
- активные обязательства/события;
- актуальную экономику;
- важные UNKNOWN;
- критические правила.

Целевой размер: примерно 5–15 KB. Не раздувать историей.

### `world_save.json`
Архивный широкий snapshot мира и истории.

**НЕ обновлять во время обычных RP-сцен.**
Обновлять только при крупной консолидации: конец большой арки/игрового дня, миграция в новый чат при необходимости, каждые ~20–30 значимых checkpoint или по прямой просьбе пользователя.

### Journal
Отдельные `journal/save_vNNNN.json` в нормальном режиме **не создавать**. GitHub commit history уже является журналом изменений `live_state.json`.

## 2. Приоритет источников

1. Последняя прямая коррекция пользователя.
2. `live_state.json`.
3. `world_save.json` для широкого исторического/мирового контекста.
4. GitHub commit history для проверки конкретного старого состояния.
5. Память отдельного чата.

`UNKNOWN` не заменять догадкой.

## 3. Новый чат

При старте нового чата:
1. Один раз прочитать `MASTER_SAVE_PROTOCOL.md`.
2. Один раз прочитать `live_state.json` и запомнить его SHA.
3. Читать `world_save.json` только если реально нужен широкий исторический/мировой фон. Для обычного продолжения сцены он не обязателен, если `live_state.json` достаточен.
4. Продолжать строго с `last_scene.continue_from`.

В уже идущем чате не перечитывать файлы перед каждой репликой.

## 4. Когда делать checkpoint

Не сохранять после каждой реплики, взгляда, шага, оплаты или отдельной мелочи.

Сохранять на **естественной границе смысловой сцены**, когда важно пережить перенос в новый чат: изменились локация, время, отношения, состав группы, деньги, контракт, важное знание NPC, активное событие или точка продолжения.

Несколько связанных действий объединять в один checkpoint.

Пример: поручение + передача денег + уточнение адреса + прощание = один checkpoint, если это одна непрерывная сцена.

## 5. ONE-WRITE checkpoint

Нормальный путь после значимой сцены:

1. Использовать рабочее состояние текущего чата.
2. НЕ читать `world_save.json`.
3. НЕ создавать journal-файл.
4. Обновить компактный `live_state.json`:
   - `save_version += 1`;
   - world time;
   - Маэстро location/state/cash;
   - `last_scene`;
   - только реально изменившиеся текущие NPC/события/отношения/экономику/UNKNOWN.
5. Сделать **ровно один `update_file`** для `live_state.json` с сохранённым SHA.
6. После успеха запомнить возвращённый `content_sha` для следующего checkpoint.
7. Commit message: `LIVE vN — <короткое описание>`.

Никаких дополнительных GitHub read/write в нормальном checkpoint не делать.

## 6. SHA conflict

Только если GitHub отклонил запись из-за SHA:
1. прочитать свежий `live_state.json`;
2. сравнить версию;
3. объединить изменения без потерь;
4. повторить один update с новым SHA.

Не читать большой `world_save.json`, если конфликт не требует исторической проверки.

## 7. Экономика

- Личная касса отдельно от promo/project funds.
- После публичного выступления обязательно: income / expense / net / new personal cash.
- Если сцена денег не меняла — не раздувать файл дополнительным ledger.
- Детальный исторический ledger хранится в archive snapshot/commit history, а не в каждом `live_state`.

## 8. Нельзя

- переписывать `world_save.json` после обычной сцены;
- читать полный SAVE перед каждой репликой/checkpoint;
- создавать отдельный journal на каждый checkpoint;
- делать больше одного GitHub write без технической необходимости;
- сохранять микрореплики;
- придумывать UNKNOWN;
- ретконить без прямой коррекции пользователя;
- решать за Маэстро его реплики, чувства, решения или значимые действия;
- давать NPC невозможные знания;
- смешивать личные и проектные деньги.

## 9. Периодическая консолидация

Отдельно от RP, примерно раз в 20–30 значимых LIVE checkpoint или по запросу пользователя:
- собрать актуальный `live_state` + нужную историю commit'ов;
- обновить `world_save.json` как новый архивный snapshot;
- затем продолжить обычный ONE-WRITE режим.

Консолидация не должна запускаться автоматически внутри обычного игрового ответа.

## 10. Цель по скорости

Нормальный checkpoint = **один небольшой `update_file`**.

Платформа не гарантирует жёсткое время ответа, но мастер не должен выполнять тяжёлые операции, если это не вызвано конфликтом или консолидацией.

## 11. Песни и точный текст

Политика песен хранится в `rules/SONG_ARCHIVE_WRITE_RULE.md`, а аудит статусов — в `memory/songs.json`.

- Перед построчной реакцией на пользовательскую адаптацию сначала проверить её статус в `memory/songs.json` и использовать полный файл, если он существует.
- `FULL_CANONICAL` означает только физически проверенный полный текст в одном UTF-8 файле `song_archive/`.
- Если полного текста нет, не подменять его оригиналом песни, веб-текстом, пересказом или догадкой.
- После того как пользователь даёт новый/исправленный полный текст песни, сохранить его целиком и дословно в одном файле, затем обязательно прочитать файл обратно и проверить отсутствие обрыва.
- Если запись физически обрезалась, файл не считать каноничным: удалить/карантинировать его и оставить статус `PARTIAL_EXACT`, `TEXT_LOST` или `FULL_LEGACY_SHARDS` по фактическому состоянию.
- Важные пользовательские адаптации нельзя оставлять только в summary сцены.
- Сам факт исполнения и реакция публики могут храниться в LIVE, но текст песни хранится отдельно.
