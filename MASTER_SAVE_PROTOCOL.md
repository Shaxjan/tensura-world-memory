# Tensura World Memory — Fast Master Save Protocol

Этот файл задаёт обязательный порядок работы мастера с `world_save.json`.

## 1. Источник истины

`world_save.json` — единственный актуальный источник состояния симуляции между чатами.

При конфликте между памятью отдельного чата и SAVE приоритет имеет SAVE, кроме случаев, когда пользователь прямо исправляет данные.

`UNKNOWN` никогда не заменять догадкой.

## 2. Быстрый режим — главное правило

### Новый чат / перезапуск

Только при входе в новый чат, после потери контекста или по прямой просьбе пользователя:

1. Один раз полностью прочитать `world_save.json` через подключённый GitHub.
2. Один раз прочитать этот `MASTER_SAVE_PROTOCOL.md`.
3. Запомнить в текущем контексте:
   - полный SAVE;
   - текущий `save_version`;
   - текущий blob SHA файла.
4. Продолжать только с `current_state.last_scene.continue_from`.

### Внутри уже идущего чата

НЕ перечитывать весь `world_save.json` перед каждым ответом или каждой сценой.

Использовать уже загруженный SAVE + события текущего чата как рабочее состояние мира.

Повторно читать полный SAVE только если:
- чат перезапущен / потерян контекст;
- GitHub сообщает конфликт SHA;
- пользователь или другой процесс изменил SAVE извне;
- мастер не уверен, что его локальное рабочее состояние актуально;
- пользователь прямо просит контрольную сверку.

## 3. Когда сохранять

Не делать GitHub commit после каждой реплики, взгляда, шага или короткого обмена фразами.

Сохранять после **значимой сцены или естественной границы сцены**, когда изменилось хотя бы одно из следующего:
- время заметно продвинулось;
- Маэстро или важный NPC сменил локацию;
- появились/изменились важные знания персонажей;
- изменились отношения или обязательства;
- изменились деньги, имущество, контракт или фонд;
- активировано, завершено или существенно изменено событие;
- принято значимое решение;
- завершён разговор/эпизод, последствия которого важно пережить при переносе в новый чат.

Несколько коротких реплик одной непрерывной сцены объединять в одно сохранение.

## 4. Быстрое сохранение после значимой сцены

Если мастер в этом же чате уже имеет актуальный SAVE и актуальный SHA:

1. НЕ скачивать весь файл повторно.
2. Применить изменения сцены к рабочей копии SAVE в контексте.
3. Увеличить `save_version` ровно на 1.
4. Провести короткую проверку целостности только затронутых данных.
5. Записать полное обновлённое содержимое обратно в `world_save.json` через GitHub, используя сохранённый актуальный SHA.
6. Commit message: `SAVE vN — <короткое описание сцены>`.
7. После успешной записи сохранить возвращённый GitHub новый `content_sha` как актуальный SHA для следующего сохранения.

Таким образом между сохранениями в одном чате не требуется повторный `fetch_file`.

### Если запись отклонена из-за SHA/conflict

Только тогда:
1. получить свежий `world_save.json`;
2. сравнить версии;
3. объединить новые события текущего чата со свежим SAVE без потери чужих изменений;
4. записать снова с актуальным SHA.

Никогда не перезаписывать конфликт вслепую.

## 5. Что обновлять

### `current_state`

По необходимости обновлять:
- world time;
- location Маэстро;
- состояние Маэстро;
- personal cash;
- `last_scene.summary`;
- `last_scene.continue_from`;
- active storylines;
- pending consequences.

`continue_from` должен быть точной точкой, откуда новый чат сможет продолжить без додумывания действий Маэстро.

### `timeline`

Значимая завершённая сцена получает новую запись с уникальным ID.

Хранить только полезные факты:
- время;
- место;
- участников;
- подтверждённые события;
- последствия.

Не превращать timeline в дословную копию всего диалога.

### `characters`

Для реально затронутых персонажей обновлять:
- location;
- status;
- goals, если они изменились;
- `knows` / `does_not_know`;
- last_confirmed_appearance;
- важные notes.

NPC не получают знания без реалистичного источника.

### `events`

События разделять на:
- `active`;
- `scheduled`;
- `completed`.

Автономные события мира продолжаются независимо от Маэстро, если ничто им не мешает.

### `relationships`

Менять только при наличии причины в сцене.

Отношение A→B не обязано быть равно B→A.

### `economy`

Критически важно:
- личная касса Маэстро хранится отдельно от промо- и проектных бюджетов;
- после публичного выступления фиксировать доход, расход, чистый результат и новый баланс;
- не восстанавливать деньги приблизительно;
- итоговая касса должна сходиться с подтверждённым журналом операций.

## 6. Что запрещено

- перечитывать весь SAVE перед каждой обычной репликой без причины;
- делать commit после каждой микрореплики;
- придумывать недостающие факты;
- заменять `UNKNOWN` вероятным вариантом;
- ретконить подтверждённую историю без прямого исправления пользователя;
- выбирать реплики, чувства, решения или значимые действия за Маэстро Арлекино;
- телепортировать NPC или менять их знания без причины;
- смешивать личные деньги Маэстро с отдельными фондами;
- при SHA-конфликте перезаписывать файл вслепую.

## 7. Короткий контроль перед commit

Проверять в первую очередь только затронутые сценой области:
- `current_state` соответствует новой сцене;
- `last_scene` и `continue_from` точны;
- касса сходится, если были деньги;
- знания NPC логичны, если появились новые сведения;
- новые локации физически возможны;
- события правильно находятся в active / scheduled / completed;
- новая версия = предыдущая + 1.

Полную глобальную ревизию всей базы проводить только периодически, при миграции в новый чат, после крупной сюжетной арки или при подозрении на противоречие.

## 8. История версий

GitHub commit history является журналом SAVE и страховкой от ошибок.

Отдельные файлы `world_save_v2.json`, `world_save_v3.json` и т. п. создавать не нужно. Рабочим остаётся один `world_save.json`.
