# Tensura World Memory — Delta Pointer Save Protocol

Цель: сохранять симуляцию компактно, без переписывания большого архива, и не терять точные коррекции пользователя.

## 1. Текущая архитектура

### `live_state.json`
Это **компактный указатель**, а не полный SAVE.

Нормальная форма:
```json
{"v":124,"parent":"<commit sha>","delta":"live_v124","economy":"ECONOMY_MODEL_v1"}
```

### `live_vNNN/delta.json`
Это актуальный компактный checkpoint сцены. Он хранит только то, что необходимо для продолжения: время, место, изменившиеся отношения/обязательства/знания, деньги, последнее событие и точку продолжения.

### `world_save.json`
Широкий архивный snapshot. Не переписывать после каждой сцены. Использовать для старого/широкого контекста и обновлять только при крупной консолидации.

### `memory/`
Категорийный аудит/индекс: деньги, места, слова, отношения, действия, песни. Это вспомогательная долговременная память и контроль противоречий, а не замена live pointer.

### `song_archive/` и `song_fragments/`
Тексты песен хранятся отдельно от LIVE. Политика — `rules/SONG_ARCHIVE_WRITE_RULE.md`; реестр статусов — `memory/songs.json`.

## 2. Приоритет источников

1. Последняя прямая коррекция пользователя.
2. Текущий разговор после последнего SAVE, если он ещё не checkpointed.
3. `live_state.json` -> указанный `live_vNNN/delta.json`.
4. Более поздние корректирующие LIVE deltas/retcons.
5. `world_save.json` для широкого исторического контекста.
6. GitHub commit history для проверки старого точного состояния/слов.
7. `memory/` как сводный индекс и сигнал о потерянных/отменённых фактах.
8. Память отдельного чата.

`UNKNOWN` не заменять догадкой.

## 3. Новый чат

При старте нового чата:
1. Прочитать `MASTER_SAVE_PROTOCOL.md`.
2. Прочитать `live_state.json`.
3. Прочитать указанный им `live_vNNN/delta.json`.
4. Если нужен старый/широкий контекст — читать `memory/` и/или `world_save.json` только по необходимости.
5. Продолжать с сохранённой точки; не переигрывать сцену и не придумывать пропуски.

Для песни: сначала проверить `memory/songs.json`, затем использовать только указанный проверенный полный файл/фрагмент.

## 4. Когда делать checkpoint

Не сохранять каждый взгляд, поцелуй, шаг или короткую реплику.

Сохранять на естественной смысловой границе, особенно если изменились:
- время/локация;
- деньги;
- отношения;
- контракт/обязательство;
- важное знание NPC;
- турнир/фестиваль/проект;
- завершилось публичное выступление;
- появился важный точный пользовательский текст;
- перед переносом в другой чат.

Несколько микродействий одной сцены объединять.

## 5. Нормальный checkpoint

Обычный checkpoint в текущей архитектуре — **две последовательные записи**:

1. Создать `live_vNNN/delta.json` с новым номером версии.
2. После успешного commit обновить `live_state.json`, чтобы `v`/`delta` указывали на новый checkpoint, а `parent` фиксировал commit нового delta.

Не делать эти две записи параллельно. Сначала delta, затем pointer.

Commit delta: `LIVE vN — <короткое описание>`.
Commit pointer: `LIVE state -> vN` или эквивалентно.

## 6. SHA conflict

Если обновление `live_state.json` отклонено по SHA:
1. получить свежий pointer;
2. проверить его версию;
3. не затирать чужую/более новую запись;
4. при необходимости объединить изменения и только затем обновить pointer.

Не переписывать `world_save.json` ради обычного SHA conflict.

## 7. Экономика

- 100c = 1s; 100s = 1g.
- Личная касса отдельно от promo/project funds и денежных float у порученцев.
- После каждого реально завершённого публичного выступления: income / expense / net / new personal cash.
- Не создавать деньги из реакции толпы: использовать `ECONOMY_MODEL_v1` и реальную ликвидность публики.
- Репутация сильнее влияет на размер публики, чем на чаевые с человека.

## 8. Контроль персонажа и знаний

- Арлекино/Маэстро полностью контролируется пользователем: не придумывать его реплики, решения, чувства и значимые действия.
- NPC и мир автономны.
- Знание NPC должно иметь причинный канал: SOURCE -> TRANSMISSION -> TIME -> RECIPIENT.
- Не передавать NPC сведения из чужих приватных сцен.
- Только Рена говорит «павлин».
- Jura — регион; JTF ещё нет.
- Falmuth, не Farmenas.
- Поручение Верна в Дваргон не связано с Ореном.
- Гарет и Верн знают точную гостиницу в мире, но её название неизвестно GM и не должно быть придумано.

## 9. Ретконы

Прямая пользовательская коррекция отменяет противоречащую старую запись. Отменённые сцены можно хранить исторически, но нельзя снова переносить в канон.

Если новый LIVE специально исправляет knowledge leak, инструментальную непрерывность, деньги или текст песни — новая коррекция приоритетна.

## 10. Песни

- Одна песня = один полный UTF-8 файл, **когда это технически возможно и файл реально проверен**.
- `FULL_CANONICAL` ставится только после обратного чтения полного файла.
- Не доверять названию коммита «full exact» без проверки содержимого.
- Если файл обрезан — удалить/карантинировать его и понизить статус.
- Если полного текста нет, не использовать оригинал, web, пересказ или догадку для заполнения пользовательской адаптации.
- `PARTIAL_EXACT` хранить в `song_fragments/`.
- `TEXT_LOST` сохраняет факт песни/исполнения, но не фальшивый текст.
- `FULL_LEGACY_SHARDS` означает: весь точный текст существует в исторических shards, но единого проверенного файла сейчас нет.
- После нового полного пользовательского текста: сохранить сразу и проверить чтением.

## 11. Периодическая консолидация

По запросу пользователя, в конце большой арки/дня или после большого числа checkpoint можно:
- сверить live pointer + deltas + category memory + нужную commit history;
- обновить `world_save.json` новым широким snapshot;
- провести аудит песен/денег/UNKNOWN;
- затем продолжить обычный delta-pointer режим.

## 12. Нельзя

- превращать `live_state.json` обратно в большой SAVE без отдельного решения;
- переписывать `world_save.json` после обычной сцены;
- придумывать UNKNOWN;
- смешивать личные и проектные деньги;
- решать за Арлекино;
- давать NPC невозможные знания;
- считать обрезанный текст песни полным;
- молча восстанавливать потерянную адаптацию по оригиналу.
