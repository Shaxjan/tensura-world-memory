# Tensura World Memory — Authoritative Runtime v1.0.1 Protocol

Цель: живую симуляцию ведёт проверяемый движок; мастер описывает результат, но не подменяет движок. Состояние сохраняется быстро через append-only runtime и не требует переписывать большой SAVE.

## 1. Текущий источник истины

### `runtime/runtime_state.json`
Главный LIVE-pointer. Нормальный режим: `mode = engine_authoritative`.

После hotfix текущий runtime использует engine `1.0.1`.

Ключевые поля:
- `base_checkpoint` — базовый portable checkpoint;
- `base_state_hash` — hash базы;
- `journal_base_seq` — sequence, уже включённый в base checkpoint;
- `journal_seq` — последний подтверждённый runtime event;
- `head_state_hash` — ожидаемый hash после replay;
- `last_event` — последний journal-файл, если поле существует;
- `legacy_rollback` — точная pre-cutover точка v159.

### `runtime/checkpoints/`
`runtime/checkpoints/cutover_v159.json` — неизменяемая стартовая база v1.0. Не переписывать её.

### `runtime/journal/jNNNNNN.json`
Append-only авторитетные события. Один файл = один проверенный переход состояния. Старый event не редактировать.

### `runtime/requests/rNNNNNN.json`
Append-only входящие команды для удалённого runtime. Это **предпочтительный путь для ChatGPT-мастера**.

### `live_state.json`
Замороженный legacy-маркер v159 и rollback-anchor. После cutover он НЕ является текущим SAVE.

`world_save.json`, `live_v*/`, `memory/` — исторический контекст и аудит. Они не перекрывают более новый runtime journal.

## 2. Старт нового чата / нового мастера

1. Прочитать `MASTER_SAVE_PROTOCOL.md`.
2. Прочитать `runtime/runtime_state.json`.
3. Убедиться: `format=TENSURA_RUNTIME_POINTER`, `mode=engine_authoritative`.
4. Для engine `1.0.1` использовать `sim_engine/v101_repository.py` / `WorldV101`, если доступно локальное исполнение Python.
5. При полном восстановлении: загрузить `base_checkpoint`, replay строго от `journal_base_seq+1` до `journal_seq`, проверить `head_state_hash`.
6. После успешного восстановления **не перечитывать весь архив на каждом сообщении**. В рамках того же чата держать восстановленное состояние/последний GM packet как рабочий контекст и перед каждым новым write проверять только свежий маленький pointer.
7. Если нужен широкий старый контекст — читать `memory/`, legacy deltas или `world_save.json` только по необходимости.

`UNKNOWN` не заменять догадкой.

## 3. Быстрый удалённый игровой ход — ОБЯЗАТЕЛЬНЫЙ путь для ChatGPT-мастера

Мастер не должен вручную изображать выполнение движка и затем забывать сохранить результат.

Для каждого нового действия пользователя:

1. Прочитать свежий `runtime/runtime_state.json`.
2. `seq = journal_seq + 1`.
3. Создать ровно один новый файл `runtime/requests/rNNNNNN.json`.
4. Формат:

```json
{
  "format": "TENSURA_TURN_REQUEST",
  "schema_version": 1,
  "seq": 2,
  "event_key": "уникальный-ключ-хода",
  "event_type": "player_turn",
  "request": {
    "raw_text": "ДОСЛОВНЫЙ текст пользователя"
  }
}
```

5. Не создавать journal вручную. Workflow `Tensura Runtime Turn` сам:
   - восстанавливает текущее состояние;
   - выполняет движок;
   - создаёт `runtime/journal/jNNNNNN.json`;
   - обновляет `runtime/runtime_state.json` и `head_state_hash`.
6. Дождаться появления соответствующего journal event / нового `journal_seq`.
7. Прочитать новый journal event и отвечать пользователю **из его `result` и `gm_packet`**.

Если journal не появился, ход ещё не авторитетен. Нельзя выдавать выдуманный результат вместо него.

## 4. Другие типы runtime request

### `scene_resolution`
Когда уже существует реальный pending и мир/NPC получил причинно установленный результат:

```json
{
  "format": "TENSURA_TURN_REQUEST",
  "schema_version": 1,
  "seq": 3,
  "event_key": "уникальный-ключ-resolution",
  "event_type": "scene_resolution",
  "request": {
    "pending_id": 7,
    "payload": {"outcome": "accepted"},
    "resolver": "gm"
  }
}
```

Использовать только разрешённые typed outcome. Generic resolution не обходит деньги, бой, магию, лечение, межрегиональные маршруты, рынок, силу и навыки.

### `narration`
Отдельный runtime event нужен только если проект явно требует записать narration. Обычная художественная подача уже подтверждённого engine result не должна менять state.

## 5. Локальное перемещение v1.0.1

Известное место внутри текущего города — конечное действие, а не вечный `pending`.

Для текущей Эуразании source-grounded места берутся из `memory/places.json`, включая:
- большой тренировочный двор Борги;
- малый боевой/тренировочный двор;
- западное тренировочное поле;
- дворец Кариона;
- торговую улицу;
- вечернюю рыночную площадь;
- район гостиниц / post-yards.

Пока точная внутригородская геометрия не откалибрована, обычный переход между известными точками использует **12 минут как prospective mechanical default**. Это игровая механика с момента v1.0.1, а не утверждение о старой канонической географии.

Переход времени обязан запускать тот же autonomy scheduler.

Повтор команды к месту, где игрок уже находится, не должен снова тратить время.

Неизвестное место или реальный поиск неизвестного объекта может оставаться pending.

## 6. Pending не должен парализовать игру

`scene_pending` означает только: конкретный внешний исход пока не установлен.

Нельзя:
- повторять одну и ту же фразу пользователя бесконечно;
- создавать дубликаты одного unresolved navigation;
- останавливать обычное перемещение к известному месту;
- в narration самостоятельно решать согласие NPC, неизвестное присутствие, выплату или иной скрытый outcome.

Если одинаковый unresolved navigation уже существует, повтор должен ссылаться на существующий pending, а не плодить новый.

## 7. Sequence, idempotency и конфликты

Перед каждым request прочитать свежий pointer.

Следующий request/event = `journal_seq + 1`.

Если `rNNNNNN` или `jNNNNNN` уже существует либо pointer ушёл вперёд:
- не перезаписывать файлы;
- перечитать pointer;
- проверить, был ли текущий `event_key` уже выполнен;
- использовать следующий свободный sequence только после восстановления актуального head.

Один и тот же `event_key` не должен дважды менять мир.

## 8. Производительность

В одном и том же игровом чате запрещено без причины заново читать:
- все legacy deltas;
- весь `world_save.json`;
- весь song archive;
- полный исторический GitHub на каждом ходе.

Нормальный удалённый ход после первоначальной загрузки:
`маленький pointer read -> один request write -> runtime-bot -> один journal read`.

GitHub всё ещё не является миллисекундным игровым сервером. Если очередь остаётся заметно медленной, следующий инфраструктурный шаг — постоянный Python runtime + SQLite/PostgreSQL; LLM остаётся мастером/интерфейсом.

## 9. Экономика

- 100c = 1s; 100s = 1g.
- Личная касса отдельно от family/promo/project funds и денежных float.
- После завершённого публичного выступления: income / expense / net / new personal cash.
- `ECONOMY_MODEL_v1` остаётся правилом экономики.
- Неизвестная цена/ликвидность не заменяется лабораторным значением.
- Остаток instrument float Верна остаётся `UNKNOWN`, пока не придёт причинный отчёт/возврат/расход.

## 10. Контроль персонажа и знания

- Пользователь единолично контролирует Арлекино: его диалог, чувства, решения и значимые действия.
- NPC и мир автономны.
- Знание NPC требует причинного канала: SOURCE -> TRANSMISSION -> TIME -> RECIPIENT.
- Не переносить сведения из чужих приватных сцен.
- Только Рена говорит «павлин».
- Jura — регион; JTF ещё нет.
- Falmuth, не Farmenas.
- Поручение Верна в Дваргон не связано с Ореном.
- Гарет и Верн знают точную гостиницу в мире, но её название UNKNOWN для GM и не должно быть придумано.

## 11. Ретконы и repair

Прямая коррекция пользователя отменяет противоречащую старую запись.

После cutover текущий реткон/repair — новый append-only runtime transition. Старый journal event задним числом не редактировать.

Если мастер произнёс сцену, но event не был journaled, эта проза сама по себе не считается движением времени/денег/локации. Восстановление такого потерянного намерения делается отдельным явным recovery request.

## 12. Rollback

`runtime/runtime_state.json.legacy_rollback` хранит точную pre-cutover точку v159 и blob SHA.

Emergency rollback:
1. остановить новые runtime writes;
2. проверить anchor/hash;
3. сохранить текущий runtime head;
4. восстановить ровно `legacy_rollback.pointer`;
5. пометить runtime как rollback/изолировать его;
6. не переносить новые runtime events обратно в legacy автоматически.

## 13. Песни

- Одна песня = один полный UTF-8 файл, когда полный пользовательский текст доступен.
- `FULL_CANONICAL` только после обратного чтения файла.
- Не восстанавливать потерянную пользовательскую адаптацию по оригиналу.
- `PARTIAL_EXACT` хранить как fragment; `TEXT_LOST` не подменять выдуманным текстом.

## 14. Нельзя

- считать `live_state.json` текущим SAVE;
- создавать новые обычные `live_vNNN` после cutover;
- отвечать результатом принятого игрового действия, если соответствующий runtime event не создан;
- вручную менять pointer раньше journal event;
- редактировать подтверждённый journal event;
- придумывать `UNKNOWN`;
- смешивать личные и проектные деньги;
- решать за Арлекино;
- давать NPC невозможные знания;
- превращать pending в факт только текстом мастера;
- бесконечно держать известное локальное перемещение в pending.
