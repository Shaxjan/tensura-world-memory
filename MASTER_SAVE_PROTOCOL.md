# Tensura World Memory — Authoritative Runtime v1.0.3 Protocol

Цель: живую симуляцию ведёт проверяемый движок; мастер описывает результат, но не подменяет движок. Обычный игровой ход идёт через компактный session fast-path, а наблюдаемая сцена должна быть живой и причинной, а не пустой из-за отсутствия заранее сохранённых NPC.

## 1. Источник истины

### `runtime/runtime_state.json`
Главный LIVE-pointer. Нормальный режим: `mode = engine_authoritative`.

Для v1.0.3:
- `engine_version = 1.0.3`;
- `base_checkpoint` — текущий compact base;
- `journal_base_seq` — уже включённый в base sequence;
- `journal_seq` — последний подтверждённый event;
- `head_state_hash` — hash после replay;
- `session_state = runtime/session_state.json` — быстрый read-model текущей игровой сессии.

### `runtime/session_state.json`
Компактный неавторитетный read-model, построенный только из авторитетного runtime. Он нужен, чтобы мастер не перечитывал checkpoint и всю историю на каждом сообщении.

Он содержит время, текущую локацию, деньги при Арлекино, личные деньги Арлекино вне кошелька, итог последнего хода и текущую living scene: фоновые люди, прямые наблюдения именованных NPC и pending.

Если `session_state.journal_seq` совпадает с pointer, в текущем уже синхронизированном чате мастер использует его напрямую. При новом чате, конфликте seq/hash или ошибке нужен full replay.

### Остальные файлы
- `runtime/checkpoints/` — immutable portable snapshots;
- `runtime/journal/jNNNNNN.json` — append-only авторитетные переходы;
- `runtime/requests/rNNNNNN.json` — входящие пользовательские команды;
- `live_state.json` — замороженный legacy v159 / rollback-anchor;
- `world_save.json`, `live_v*/`, `memory/` — история и аудит, они не перекрывают runtime.

## 2. Старт нового чата

1. Прочитать `MASTER_SAVE_PROTOCOL.md`.
2. Прочитать `runtime/runtime_state.json`.
3. Прочитать `runtime/session_state.json`, если его seq совпадает с pointer.
4. Один раз проверить full replay: base checkpoint + journal после `journal_base_seq` до `journal_seq` -> `head_state_hash`.
5. После успешной проверки держать session state в контексте чата.
6. Не перечитывать весь архив на каждом сообщении.
7. Старый legacy pending не использовать, если он уже закрыт новым runtime event.

`UNKNOWN` не заменять догадкой.

## 3. Быстрый игровой ход

Для каждого нового действия пользователя:

1. Проверить только свежий `runtime/runtime_state.json`.
2. Если pointer seq совпадает с локально известным — full replay не нужен.
3. Создать ровно один `runtime/requests/rNNNNNN.json`, где `seq = journal_seq + 1`, а `raw_text` — дословный текст пользователя.
4. Workflow `Tensura Runtime Turn` сам восстанавливает state, выполняет текущий engine, создаёт новый journal event, обновляет pointer и `runtime/session_state.json`.
5. Дождаться нового session state.
6. Для обычного ответа читать session state; journal нужен только для подробного результата/аудита.
7. При stale seq/hash сначала синхронизироваться и не повторять эффект вслепую.

Нельзя выдавать игровой исход до подтверждённого runtime event.

## 4. Обязательный HUD в КАЖДОМ игровом ответе

Каждый обычный игровой ответ явно показывает:
- `Время`;
- `Место`;
- `При мне`;
- `Мои деньги вне кошелька`.

Рекомендуемый формат:

`Время: T+131 ~08:00 | Место: большой тренировочный двор Борги | При мне: 26g 05s 92c | Мои деньги вне кошелька: у Верна — остаток UNKNOWN (из переданных 50s)`

Семейная касса, project funds, promo funds, earmarked gifts/expenses и payables не являются личными деньгами Арлекино и не попадают в строку `Мои деньги вне кошелька`.

Если точный остаток личных денег у другого держателя неизвестен, показывать `UNKNOWN`, а не исходную переданную сумму как текущий баланс.

## 5. Чистая игровая наррация

В нормальной игре не показывать `engine_authoritative`, `journal_seq`, hashes, migration diagnostics, названия таблиц и внутренние объяснения resolver.

Сначала HUD, затем обычная живая сцена. Технические данные показывать только при ошибке, конфликте, recovery или по прямому запросу пользователя.

## 6. Living Scene Runtime

`UNKNOWN` местонахождения именованного NPC не означает пустую локацию.

Для известной локальной точки движок может prospectively создать причинно допустимых анонимных людей: бойцов и тренировочные группы на тренировочном дворе, помощников/работников при площадке, стражу/служащих у дворца, торговцев/грузчиков/прохожих на торговых точках, работников/постояльцев в гостиничном районе.

У каждого ambient entity есть стабильный engine id, роль, наблюдаемое занятие и срок присутствия. Они сохраняются между близкими ходами и не должны исчезать только потому, что пользователь отправил новое сообщение.

Эти люди — `NON_CANON_MECHANICAL_PROSPECTIVE`: они становятся частью мира с момента engine materialization, но не являются ретроактивным утверждением о прошлом.

Мастер вправе естественно описывать ambient scene из `session_state.scene.ambient`. Фраза «никого подтверждённого нет» запрещена, если runtime уже содержит видимых фоновых людей.

Нельзя автоматически превращать фонового человека в старого знакомого, важного именованного NPC или носителя приватной информации.

## 7. Именованные NPC и локальный поиск

Именованный NPC не появляется потому, что так удобнее сцене.

Для его позиции требуется сохранённая точная позиция, prospective routine/schedule, разрешённая движком, прямое наблюдение либо причинное свидетельство.

v1.0.3 первой калибрует локальную рабочую рутину Борги, потому что его связь с тренировочными площадками уже сохранена, а текущий авторитетный ход прямо ищет его.

Поиск Борги на известной площадке — конечное действие: 6 игровых минут; за это время работает autonomy scheduler; текущая площадка получает living population; результат — `found`, `lead` или `not_found_no_lead`.

`lead` — свидетельство локального человека, а не всеведение. Оно не гарантирует, что Борга будет оставаться в указанной точке до прихода Арлекино.

Если для другого именованного NPC prospective routine ещё не калибрована, его точная позиция остаётся guarded `UNKNOWN`.

## 8. Локальное перемещение

Известная точка в текущем городе — конечное действие, не вечный pending.

Движок распознаёт место, назначает prospective время пути, двигает мировой clock, запускает автономность, фиксирует прибытие, materializes/поддерживает living scene для наблюдаемой точки и не выдумывает именованного NPC, оплату или встречу без causal result.

Повтор команды в уже достигнутую точку не списывает время повторно.

## 9. Pending

Pending нужен только там, где исход действительно нельзя безопасно разрешить текущей механикой. Narration не превращает pending в факт.

При обновлении engine старый pending может быть закрыт новым system runtime event только если исходное действие уже было явно выбрано пользователем. Такой resume не является новым решением за игрока.

Generic resolver нельзя использовать для обхода механик денег, боя, магии/лечения, рынка, силы или межрегионального travel.

## 10. Деньги

- 100c = 1s; 100s = 1g.
- Личная касса отдельно от family/project/promo средств.
- После реально завершённого публичного выступления: income / expense / net / new personal cash.
- Неизвестный entrusted float остаётся `UNKNOWN` до причинного отчёта/расхода/возврата.
- У Верна переданный principal 50s не равен текущему остатку: текущий остаток `UNKNOWN`.
- Не создавать деньги из реакции толпы; использовать `ECONOMY_MODEL_v1` и причинную ликвидность.

## 11. Контроль Арлекино и знания

- Арлекино/Маэстро полностью контролирует пользователь.
- Не придумывать его реплики, чувства, решения и значимые действия.
- NPC и мир автономны.
- Знание NPC требует `SOURCE -> TRANSMISSION -> TIME -> RECIPIENT`.
- Не передавать NPC приватные сведения без канала.
- Только Рена говорит «павлин».
- Jura — регион; JTF ещё нет.
- Falmuth, не Farmenas.
- Поручение Верна в Дваргон не связано с Ореном.
- Гарет и Верн знают точную гостиницу в мире; GM не знает её названия и не придумывает его.

## 12. Retcon / repair

Прямая коррекция пользователя отменяет противоречащую старую запись. После cutover repair оформляется новым runtime transition. Старый journal event не редактировать.

## 13. Checkpoint / compaction

При смене engine semantics или периодически: replay текущего base + journal до head; проверить hash; экспортировать новый portable checkpoint в новый файл; проверить roundtrip; обновить pointer и `journal_base_seq`; старые checkpoint/journal не удалять.

Новая версия engine не должна replay старых событий под изменившейся семантикой, если это меняет их результат. В таком случае сначала compact старый подтверждённый head, затем начинать новые события новой версией.

## 14. Rollback

`legacy_rollback` хранит точную pre-cutover v159 точку. Emergency rollback: остановить runtime writes; проверить anchor/blob SHA; сохранить текущий runtime head; восстановить ровно legacy pointer; не переносить частично новые runtime events в legacy автоматически.

## 15. Песни

- Одна песня = один полный UTF-8 файл, когда текст реально полный и проверен.
- `FULL_CANONICAL` только после обратного чтения полного файла.
- Потерянный/обрезанный текст не восстанавливать по оригиналу или памяти.

## 16. Нельзя

- считать legacy `live_state.json` текущим SAVE;
- редактировать подтверждённый journal event;
- обновлять pointer раньше успешного event;
- придумывать `UNKNOWN`;
- трактовать отсутствие именованного NPC как отсутствие всех людей;
- смешивать личные, семейные и проектные деньги;
- решать за Арлекино;
- давать NPC невозможные знания;
- превращать causal testimony в абсолютную истину;
- показывать техничку вместо игровой сцены без необходимости;
- пропускать обязательный HUD.
