# Tensura World Memory — Authoritative Runtime v1.0.2 Protocol

Цель: живую симуляцию ведёт проверяемый движок; мастер описывает результат, но не подменяет движок. Состояние сохраняется через append-only runtime, а обычный игровой ответ не требует полного replay всей истории.

## 1. Источник истины

### `runtime/runtime_state.json`
Главный LIVE-pointer. Нормальный режим: `mode = engine_authoritative`.

Для v1.0.2:
- `engine_version = 1.0.2`;
- `base_checkpoint` — текущий compact base;
- `journal_base_seq` — уже включённый в base sequence;
- `journal_seq` — последний подтверждённый event;
- `head_state_hash` — hash после replay;
- `session_state = runtime/session_state.json` — быстрый read-model текущей игровой сессии.

### `runtime/session_state.json`
Компактный **неавторитетный read-model** для мастера. Он создаётся только из авторитетного движка и нужен, чтобы не читать большой checkpoint/journal на каждом ответе.

Он всегда содержит:
- время;
- текущую локацию;
- деньги при Арлекино;
- личные деньги Арлекино вне кошелька, если они причинно подтверждены;
- короткий итог последнего хода;
- видимых NPC / pending, если они есть.

Если `session_state.journal_seq` совпадает с ожидаемым seq текущего чата, мастер может использовать его напрямую. При конфликте, пропуске seq, новом чате или ошибке hash выполняется полный replay.

### `runtime/checkpoints/`
Portable snapshots. `cutover_v159.json` остаётся неизменяемым аварийным anchor. Новый compact base создаётся новым файлом; старый не перезаписывается.

### `runtime/journal/jNNNNNN.json`
Append-only авторитетные переходы. Старый event не редактировать.

### `runtime/requests/rNNNNNN.json`
Append-only входящие команды. Это обязательный путь для обычного удалённого игрового хода ChatGPT-мастера.

### `live_state.json`
Замороженный legacy v159 / rollback-anchor. Не является текущим SAVE.

`world_save.json`, `live_v*/`, `memory/` — исторический контекст и аудит; они не перекрывают runtime.

## 2. Старт нового чата

1. Прочитать `MASTER_SAVE_PROTOCOL.md`.
2. Прочитать `runtime/runtime_state.json`.
3. Прочитать `runtime/session_state.json`, если он существует и его `journal_seq` совпадает с pointer.
4. Для нового чата один раз проверить full replay: base checkpoint + journal после `journal_base_seq` до `journal_seq` -> `head_state_hash`.
5. После успешной проверки держать текущий session state в контексте чата.
6. Не перечитывать весь архив на каждом сообщении.

`UNKNOWN` не заменять догадкой.

## 3. Быстрый ход в том же игровом чате

Для каждого нового действия пользователя:

1. Если локально сохранённый session seq совпадает с ожидаемым — не делать full replay.
2. Создать один новый `runtime/requests/rNNNNNN.json`, где `seq = journal_seq + 1` и `raw_text` — дословный текст пользователя.
3. Workflow `Tensura Runtime Turn` сам восстанавливает state, исполняет движок, создаёт `jNNNNNN`, обновляет pointer и `runtime/session_state.json`.
4. Дождаться нового session state / journal seq.
5. Прочитать **только новый `runtime/session_state.json`** для обычного ответа. Journal читать дополнительно только если нужен технический аудит/подробный engine result.
6. Если request отклонён из-за stale seq/hash — перечитать pointer/session state и синхронизироваться; не повторять игровой эффект вслепую.

Нельзя выдавать игровой исход до подтверждённого runtime event.

## 4. Обязательный HUD в КАЖДОМ обычном игровом ответе

Каждый игровой ответ пользователю обязан явно показывать четыре поля:

- `Время` — например `T+131 ~07:54`;
- `Место` — текущая причинно подтверждённая локация;
- `При мне` — личные деньги Арлекино, физически доступные ему сейчас;
- `Мои деньги вне кошелька` — только личные средства Арлекино, находящиеся у другого держателя/в другом месте. Если точный остаток неизвестен — показать `UNKNOWN`, а не исходную переданную сумму как текущий баланс.

Рекомендуемый компактный формат:

`Время: T+131 ~07:54 | Место: большой тренировочный двор Борги | При мне: 26g 05s 92c | Мои деньги вне кошелька: у Верна — остаток UNKNOWN (из переданных 50s)`

Семейная касса, project funds, promo funds, earmarked gifts/expenses и payables **не являются личными деньгами Арлекино** и не должны попадать в строку `Мои деньги вне кошелька`.

При необходимости их можно показать отдельным блоком только если они важны для сцены или пользователь спросил.

## 5. Чистая игровая наррация

В нормальном игровом ответе не показывать без необходимости:
- `engine_authoritative`;
- `journal_seq`;
- hashes;
- migration blockers;
- названия внутренних таблиц;
- техническое объяснение, почему движок что-то разрешил.

Сначала короткий HUD, затем обычная живая сцена.

Технические поля показывать только:
- при ошибке;
- при конфликте сохранения;
- при recovery;
- по прямому запросу пользователя.

## 6. Локальное перемещение

Известная локальная точка в текущем городе — конечное действие, а не вечный pending.

Движок:
- распознаёт известную точку;
- назначает prospective механическое время пути;
- двигает мировой clock;
- запускает автономность мира за это время;
- фиксирует прибытие;
- не выдумывает присутствие NPC, встречу, оплату или событие по дороге без причинного результата.

Повтор той же команды в уже достигнутую точку не должен снова списывать время.

## 7. Pending и внешние результаты

Если исход действительно зависит от NPC/мира и не установлен, он остаётся typed pending.

Narration не имеет права превращать pending в факт. Resolver меняет только разрешённые поля конкретного outcome.

Generic scene resolution нельзя использовать для обхода механик денег, боя, силы, магии/лечения, рынка или межрегионального travel.

## 8. Деньги

- 100c = 1s; 100s = 1g.
- Личная касса отдельно от family/project/promo средств.
- После реально завершённого публичного выступления: income / expense / net / new personal cash.
- Неизвестный остаток entrusted float остаётся `UNKNOWN` до причинного отчёта/расхода/возврата.
- У Верна переданный principal 50s не равен текущему остатку: текущий остаток `UNKNOWN`.
- Не создавать деньги из реакции толпы; использовать `ECONOMY_MODEL_v1` и причинную ликвидность.

## 9. Контроль персонажа и знания

- Арлекино полностью контролируется пользователем: не придумывать его реплики, чувства, решения и значимые действия.
- NPC и мир автономны.
- Знание NPC требует SOURCE -> TRANSMISSION -> TIME -> RECIPIENT.
- Не передавать NPC приватные сведения без канала.
- Только Рена говорит «павлин».
- Jura — регион; JTF ещё нет.
- Falmuth, не Farmenas.
- Поручение Верна в Дваргон не связано с Ореном.
- Гарет и Верн знают точную гостиницу в мире; GM не знает её названия и не придумывает его.

## 10. Retcon / repair

Прямая коррекция пользователя отменяет противоречащую старую запись.

После cutover текущий retcon/repair оформляется новым runtime transition. Старый journal event не редактировать задним числом.

## 11. Checkpoint / compaction

Периодически или при смене engine semantics:
1. replay текущего base + journal до head;
2. проверить hash;
3. экспортировать новый portable checkpoint в новый файл;
4. проверить roundtrip;
5. обновить pointer: новый base, `journal_base_seq = journal_seq`;
6. старые checkpoint/journal не удалять автоматически.

## 12. Rollback

`legacy_rollback` хранит точную pre-cutover v159 точку.

Emergency rollback:
- остановить runtime writes;
- проверить anchor/blob SHA;
- сохранить текущий runtime head;
- восстановить ровно legacy pointer;
- не переносить частично новые runtime events в legacy автоматически.

## 13. Песни

- Одна песня = один полный UTF-8 файл, когда текст реально полный и проверен.
- `FULL_CANONICAL` только после обратного чтения полного файла.
- Потерянный/обрезанный текст не восстанавливать по оригиналу или памяти.

## 14. Нельзя

- считать legacy `live_state.json` текущим SAVE;
- редактировать подтверждённый journal event;
- обновлять pointer раньше успешного event;
- придумывать `UNKNOWN`;
- смешивать личные, семейные и проектные деньги;
- решать за Арлекино;
- давать NPC невозможные знания;
- показывать техничку вместо нормальной игровой сцены без необходимости;
- пропускать обязательный HUD в обычном игровом ответе.
