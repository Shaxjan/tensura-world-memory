# Этап Д: безопасное обновление архива Threads

**Обновлено 23 октября 2026 года.** Только архив и индекс; никаких публикаций, изменений профиля, фоновой браузерной автоматизации, GitHub Actions или обращений к репозиторию игры.

## Источники и принцип

**Обновление 23.10.2026:** 454 авторских корневых поста, 40 независимых редакционных карточек; пять сохранённых снимков Windsor.ai охватывают публикации за 13–23 октября, а отдельный снимок содержит 16 вероятных авторских продолжений. Поисковое поле учитывает их, но это не подтверждение полной ветки. Остальные 14 авторских ответов сознательно исключены как разговорные или поздние. См. [протокол восстановления](./index/recovery-2026-10-23.json).

Новые данные получают только из **явной выгрузки Windsor.ai** с полями \`post_id\`, \`post_timestamp\`, \`post_text\`, \`post_permalink\`, \`post_media_type\`, \`post_views\`. Может использоваться JSON вида \`{"status":"done","data":[...]}\` или зафиксированный JSON-снимок \`{"posts":[...]}\`. Внутри выгрузки должны присутствовать только записи @mirpottera.

\`snapshot_intake.js\` локально сравнивает выгрузку с индексом. Дубликаты, битые ссылки, невозможные метрики, неполные выгрузки, изменение текста у уже известного ID **не принимаются без ручной проверки**. Репосты учитываются в источнике, но не добавляются как авторские корневые публикации.

## Контрольный запуск полного архива в безопасной копии

Для завершения технического этапа 5 на машине, где репозиторий уже полностью клонирован:

```bash
python -B threads/radar/integration_gate.py --repo-root .
```

Скрипт не запускает сетевую синхронизацию и не пишет в основной индекс. Он берёт источники из текущего клона, копирует их во временную директорию, **дважды** пересобирает индекс, проверяет `verify`, проверяет побайтное совпадение с тремя сохранёнными индексными файлами, после чего запускает Python- и Node.js-наборы тестов. Если хотя бы один пункт падает, возвращает ненулевой код и JSON с ошибкой. **Пока нативный полный запуск на реальных 454 текстах не проводился; это подготовленная, а не принятая процедура.**

Последняя версия сборщика предварительно записывает новый индекс во временную папку и пытается восстановить прежние файлы при штатной ошибке записи. Аварийное отключение питания/процесса может оставить промежуточное состояние, поэтому всегда использовать точное сравнение с исходным архивом после сбоя.

## Режим 1 — предварительный просмотр (по умолчанию)

\`\`\`bash
node threads/radar/snapshot_intake.js /path/to/windsor-export.json
\`\`\`

Команда возвращает число строк, новые авторские ID, повторные ID, изменённые ID и репосты. **Ничего не пишет и не публикует.** При существующих изменениях \`needs_manual_review=true\` и ненулевой код завершения.

## Режим 2 — запись неизменяемого снимка в отдельной ветке

Только в локальном клоне на специально созданной ветке с названием \`radar-*\`:

\`\`\`bash
node threads/radar/snapshot_intake.js /path/to/windsor-export.json --write-local --date 2026-10-21
\`\`\`

Снимок создаётся в \`threads/radar/snapshots/\` с названием \`windsor-import-<date>-<hash>.json\`. Операция \`wx\` атомарно защищает существующие файлы от перезаписи. Команда не делает \`git commit\`, \`git push\`, \`merge\` и не меняет уже опубликованные посты.

**Важно:** дата \`--date\` — дата фактического получения снимка по UTC, её нельзя выставлять в будущее ради обхода ограничения актуальности. Для редакционной сетки всегда Красноярск UTC+7.

## Режим 3 — обновление производного индекса

На той же отдельной ветке, после проверки файла:

\`\`\`bash
python threads/radar/radar.py build
python threads/radar/radar.py verify
node --test threads/radar/semantic.test.js threads/radar/reserve.test.js threads/radar/snapshot_intake.test.js threads/radar/reserve-current.test.js threads/radar/semantic-safety.test.js threads/radar/snapshot-safety.test.js
python -m unittest discover -s threads/radar -p 'test_*.py'
node threads/radar/reserve_check.js 2026-10-23
\`\`\`

Python использует все \`windsor-*.json\` в порядке имён; новые \`post_id\` добавляются, переиздания сопоставляются по ID. Изменённые ранее опубликованные записи **не должны** незаметно менять смысловой архив: если входная выгрузка показывает другую редакцию текста, остановитесь и проверьте вручную.

После появления новых записей необходимо обновить \`source_index_date\` у резервных карточек, **но только после повторного поиска**. Скрипт должен отвергать использование старой даты и старого размера индекса. Нельзя автоматически переписывать статус \`scheduled\` в \`published\` у редакционных карточек без доказанного совпадения ID или ссылки.


## Важный контроль перед использованием резерва

- Дата скрининга R4 — **23 октября 2026 года**, 454 публикации, 40 редакционных карточек и 16 вероятных продолжений; 15 идей требуют усиленной редакторской проверки. После нового дня/поста повторить проверку, иначе статус должен быть `STALE_RECHECK`.
- `node .../reserve_check.js` не утверждает и не публикует концепции; запись в `scheduled` не доказывает фактическую публикацию.
- Следить за `git diff` после `radar.py build`: разрешены только ожидаемые изменения производного индекса. Не изменять `full-posts-verified.json`, архивные файлы, исходные публикации и игровые репозитории.
- Не повышать степень подтверждения 16 продолжений на основании одного временного интервала; не смешивать их с обычными комментариями.
- На текущей ветке независимая реконструкция 454/454 корней и 40/40 редакционных карточек дала ноль расхождений. Нативная пересборка остаётся открытым контрольным пунктом.

## Этап 5: проверка качества входных данных и даты

Импорт в отдельной `radar-*` ветке проверяет не только исходный текст и ссылку старого `post_id`, но и неизменяемые время публикации и тип медиа. Некорректная календарная дата, дата получения раньше любого поста и некорректная дата скрининга — причины **остановиться**, а не переходить к `NEW_STORY`.

Сборщик проверяет отсутствие исчезнувших ID и запрещает незаметную подмену исторических текстов/URL/даты/типа публикации. `verify` дополнительно сравнивает 414 исторических оригиналов с базовым архивом и запрещает пометку новых веток как полностью проверенных. Проверены оба домена `threads.com` и `www.threads.com`, поддельные хосты блокируются.

При одновременном наличии старых файлов `windsor-import-*` и новых `windsor-YYYY-*` порядок берётся из `retrieval_date_utc`, а не из названия файла. Просмотры могут обновляться, авторский текст — нет.

Проверки, выполненные без Work: **41/41 Python** и **17/17 Node.js** нативно на отдельных фикстурах. Прямой полный Node-прогон на 454-публикационном индексе и непосредственная Python-пересборка основного архива ещё не завершены. См. [протокол этапа 5](./validation-stage-5-2026-10-23.json).

## Режим защиты от одновременных обновлений

Пока запущена Python-пересборка, в `threads/radar/.build.lock` существует эксклюзивный файл .build.lock. Второй процесс остановится, не вмешиваясь в индекс. При штатном и ошибочном завершении файл снимается. После аварийного завершения проверьте PID, целостность архива и причину остановки вручную; нельзя автоматически удалять потенциально активную блокировку.

Без указания даты `reserve_check.js` теперь использует **сегодня в Красноярске, UTC+7**, а не `source_index_date`. Поэтому архив от 23.10.2026 автоматически помечается `STALE_RECHECK` начиная с 24.10.2026. Перед редакционным использованием нужна реальная синхронизация и повторный смысловой скрининг.

## Контрольный список источников R4

R4 сохраняет полные перечни 454 ID публикаций и 40 ID журнала. Не допускается использовать прежний `screening` после замены корня/карточки даже при неизменной суммарной численности. При новой синхронизации заново составлять резерв, не редактировать счётчик или список ID вручную.

Индекс дополнительно блокирует потерю уже присоединённых продолжений и ранее сохранённых карточек. Если при существующем `manifest.json` отсутствует `posts.jsonl` или `editorial.jsonl`, необходима ручная сверка, а не автоматическая сборка.

## Ограничения

1. **Нет настоящего планировщика**: запрос к Windsor.ai и получение JSON выполняются через подключённый сервис или вручную. Этот сценарий локально валидирует уже полученный файл. Сам по себе не ходит в интернет.
2. **Ответы автора:** 16 вероятных продолжений за 13–23 октября добавлены лишь в поисковое поле. Доказательства полной ветки нет; поздние/диалоговые ответы не добавляются.
3. **Источник может быть неполным или кешированным**. Сверять последнюю доступную дату и число строк.
4. **Уровень семантики ограничен**: сюжетный классификатор эвристический, а не полная экспертная разметка всех 454 авторских корневых публикаций.
5. JS-проверки выполнены в изолированном V8 с заменёнными модулями Node; 22 Python-теста индекса, поискового алгоритма и продолжений прошли напрямую. Полный нативный Node.js и Python-интеграционный прогон по клону пока не подтверждён. См. \`validation-stage-3-2026-10-23.json\`.

Пример безопасного порядка: Windsor.ai read-only -> JSON файл -> dry-run -> ручной разбор конфликтов -> \`--write-local\` в radar-ветке -> \`radar.py build\` -> тесты -> ревизия резервных идей -> Draft PR. Ни один шаг не даёт права на публикацию.
